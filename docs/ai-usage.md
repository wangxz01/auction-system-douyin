# AI 使用说明

## 1. AI 在项目中的角色

AI 主要承担**执行辅助**和**审查辅助**：

- 快速阅读代码并定位风险点
- 生成后端测试样例
- 补齐重复性接口和前端页面样板
- 整理 README 和方案文档
- 根据测试失败信息辅助定位问题

AI 不直接决定核心交易规则，关键设计由人工确认后再实现。

## 2. AI 工具清单

| 工具 | 用途 | 阶段 |
|---|---|---|
| **Claude Code (claude-opus-4-7)** | 主力对话式编程：架构讨论、代码生成、测试补齐、文档整理、git 操作 | 全程 |
| **Claude Code 内置 Plan 子代理** | 多步骤实现前的方案对齐与拆解 | 关键阶段（评论持久化、出价加固、商家工作流） |
| **Claude Code 内置 Explore 子代理** | 跨文件查找与结构盘点（替代手敲 grep） | 全程 |
| **GitHub CLI (`gh`)** | 仓库/Issue/PR 操作（由 Claude Code 调用） | 提交阶段 |
| **k6 (Grafana)** | 压测脚本运行，AI 生成脚本与结果模板 | 性能验证 |

未使用其他代码生成工具（Copilot / Cursor / Codeium 等），便于工具链可追溯。

## 3. AI 代码贡献率（粗估）

> 口径：按 `git log --shortstat` 的代码行数估算，区分核心交易路径 / 业务样板 / 测试与文档。

| 模块 | AI 主导生成 | 人工把控修订 | 备注 |
|---|---:|---:|---|
| 出价事务（`bid.go`） | ~30% | ~70% | 核心交易规则、`client_bid_id` 幂等、行锁顺序均由人工拍板 |
| 状态机与权限（`auction.go` / `authz.go`） | ~50% | ~50% | 状态转换规则人工确认，权限矩阵 AI 协助补全 |
| Redis 缓存与防击穿（`cache.go`） | ~80% | ~20% | singleflight 模式由 AI 提出，人工验证语义和测试 |
| WebSocket Hub（`hub.go` / `ws.go`） | ~50% | ~50% | 房间隔离设计人工，慢客户端踢出与 ping/pong AI 补全 |
| 商家后台样板（`admin_*.go`） | ~80% | ~20% | 增删改查接口高度模式化 |
| 后端测试（`*_test.go`） | ~85% | ~15% | AI 生成测试用例，人工补充并发与边界 case |
| 前端业务页面（`pages/*.tsx`） | ~70% | ~30% | iOS 列表/玻璃风样式人工定调，组件实现 AI 完成 |
| 前端直播间（`AuctionDetail.tsx`） | ~60% | ~40% | 交互动画与"被超越/延时"提示反复人工迭代 |
| 文档（`README.md` / `docs/*`） | ~80% | ~20% | AI 写初稿，人工校对数字、删掉未验证内容 |
| 部署模板（`Dockerfile` / `nginx.conf` / `compose.prod.yml`） | ~70% | ~30% | AI 提模板，人工对齐当前环境变量 |

**核心交易路径（出价 / 订单 / 状态机）AI 贡献率约 30-50%**，**样板与文档约 70-85%**。
项目不追求 AI 代码比例越高越好，而是追求关键决策可解释、核心路径可测试、最终结果可复现。

## 4. 人工把控的关键决策

| 决策点 | 人工把控原因 |
|---|---|
| 金额用 `*_cents` 整数字段 | 避免浮点精度影响交易规则 |
| MySQL 行锁作为一致性兜底 | Redis 不应成为唯一正确性来源 |
| `client_bid_id` 幂等键 | 防止重复点击或网络重试重复落库 |
| 状态机不可逆 | 避免订单和竞拍状态反复变化 |
| 订单权限保护 | 防止知道 auction id 就能查看他人订单 |
| `ADMIN_USERNAMES` 管理员策略 | 适合开发演示，后续可演进为正式 RBAC |
| 缓存防击穿用 singleflight 而非分布式锁 | 当前单实例部署，singleflight 足够；避免引入额外故障面 |

## 5. AI 代码使用边界

- AI 生成代码必须经过人工 `git diff` 审查。
- 核心交易链路必须有自动化测试。
- 不能把无法解释的生成代码合入核心路径。
- 不能把外部资料中的密钥、账号密码或敏感信息复制进仓库。
- 通过 `go build`、`go vet`、`go test`、`npm run lint`、`npm run build` 后才能提交。

## 6. 可追溯性

- 每次 AI 辅助产生的改动以 Conventional Commits（`feat:` / `fix:` / `style:` / `chore:` / `docs:` / `refactor:`）形式落盘，可通过 `git log` 还原阶段。
- 关键阶段在 `docs/plans/` 目录留有方案文档（如评论持久化阶段）。
- AI 不直接 push，所有提交均由人工本地复核后推送。

## 7. 典型 Prompt

### 并发风险分析

```text
检查这个出价接口在并发情况下是否会出现低价覆盖高价、重复订单或 winner 错误，并给出可测试的修复方案。
```

### 测试补齐

```text
为 0 元起拍、自动延时、封顶成交、重复 client_bid_id、并发出价写后端测试，先验证当前行为是否失败。
```

### 权限审查

```text
从攻击者视角检查订单、商家后台、上传、WebSocket 和评论接口是否存在越权或未鉴权问题。
```

### 缓存防击穿审查

```text
当前 cache.go 只有 Get/Set/Del，热点 key 过期瞬间会击穿到 MySQL。
请给出 singleflight 改造方案并附并发去重测试。
```

### 文档整理

```text
把当前项目实现整理成评审可读的方案文档，重点突出实时同步、并发控制、幂等和 AI 使用边界。
```

## 8. AI 贡献率评估总结

AI 适合承担：

- 样板代码
- 测试用例
- 文档初稿
- 风险点清单
- 重复接口串联

人工必须把控：

- 交易规则
- 一致性边界
- 安全权限
- 演示取舍
- 是否合入主分支
